**2026-08-13 — Phase 0, Madurai near-duplicate check.**

The brief's framing was specific: "three of our outlets share a wall... I cannot tell you which one a BDM was standing in," implying a literal cluster of outlets a few metres apart in Madurai. Going in, the working assumption (mine, not verified yet) was that the coordinate data would contain such a triplet, and the job was just to find it and use it as the running example for Phase 3.

It isn't there. I ran a pairwise haversine distance check within each normalized territory (script: `scripts/explore.py` + inline analysis, see `docs/data-notes.md` §3). Result: the closest pair of *genuinely differently-named* outlets in Madurai is 191 metres apart — a different block, not a shared wall. What the data actually contains is 20 pairs of outlets nationwide sitting at the *exact same* coordinates with near-identical names (casing differences, trailing spaces, `"- Branch"` suffixes), concentrated in outlet codes OA0798–OA0820.

The catch: my first pass treated the 0.0m-apart pairs as "found it, that's the Madurai case" and almost wrote them up that way. Before committing to that framing, I checked whether those pairs were empty duplicate rows or real records — and both codes in every pair independently appear in `billing-monthly.csv` with different revenue and in `visit-log.csv` with real visits. That's a different bug: duplicate outlet registration splitting one shop's history across two codes, not two adjacent-but-distinct shops that GPS can't tell apart. Same visible symptom to the client ("can't tell which outlet the BDM was at"), different root cause, different fix (a de-dupe/merge candidate list, not a verification mechanism).

Fix: `docs/data-notes.md` reports both findings separately and explicitly says the literal "3-shops-5m-apart" scenario is not reproduced in this dataset's coordinates, rather than forcing the duplicate-registration finding into that shape to match the brief's narrative. The Phase 3 design (outlet-side code, GPS demoted to anomaly-only) still holds either way — but the evidence backing it is now the real evidence, not a reach.

**2026-08-13 — Phase 2, live browser test of the Counter Conversation screen.**

Wrote `db/queries.py::fetch_manual_dues` with `SELECT response_value, created_at FROM visit_checklist_responses vcr JOIN visits v ON v.visit_id = vcr.visit_id ...` — both `visit_checklist_responses` and `visits` have a `created_at` column, and the bare `created_at` in the SELECT list is ambiguous. Postgres rejected it: `AmbiguousColumn: column reference "created_at" is ambiguous`.

I didn't catch this from reading the code — it only surfaced when I actually loaded the app in a browser at 390px and opened a Counter Conversation screen, which is exactly the kind of bug a code review skims past (the query looks fine until you remember the schema has two `created_at` columns three tables apart). Unit tests didn't catch it either, since the segmentation/scoring/normalize test suite never touches this query.

Worse side effect: the app caches one Postgres connection per session (`@st.cache_resource`) and reuses it across every screen rerun. Once this one query failed, Postgres left the connection in `InFailedSqlTransaction` state, so *every subsequent query on that connection* failed too — including completely unrelated ones like `fetch_outlets` on the next screen — until the process restarted. The visible symptom (a `fetch_outlets` traceback) was not the real bug; the real bug was three calls earlier.

Fix: qualified the column as `vcr.created_at`, and added a `try/except psycopg2.Error: conn.rollback(); raise` around the screen dispatch in `app.py` so one bad query can't permanently wedge the cached connection for the rest of the session. Take-away: with a cached long-lived DB connection, any unhandled query error becomes a session-wide outage, not a one-screen error — that needs a rollback safety net regardless of how careful the SQL is.

**2026-08-13 — Phase 3, scripted write-path test found a duplicate-key crash.**

`db/queries.py::submit_visit` generated each new visit's primary key as `f"APP-{datetime.utcnow().strftime('%Y%m%d%H%M%S%f')}-{outlet_code}"` -- a timestamp down to the microsecond, which reads as unique enough on its face. Testing the write path with `scripts/dev_verify_writes.py` (three back-to-back `submit_visit` calls to check the Verified/Partial/Unverified confidence branches), the third call crashed: `psycopg2.errors.UniqueViolation: duplicate key value violates unique constraint "visits_pkey"`. Two calls a few milliseconds apart had generated the *same* visit_id string.

Checked directly: `datetime.utcnow().strftime('%Y%m%d%H%M%S%f')` called five times in a tight loop on this machine returned the identical string all five times. Windows' clock resolution for this call is coarser than one microsecond (commonly ~15ms ticks), so "microsecond precision" was theatre — any two inserts within the same tick collide. This would not have shown up in a single manual click-through test; it only surfaced because the verification script fired requests back-to-back with no human delay between them, which is exactly what a busy BDM tapping through visits quickly could also do.

Fix: switched the ID to `f"APP-{uuid.uuid4().hex[:16]}-{outlet_code}"` -- a real uniqueness guarantee that doesn't depend on OS clock resolution. Take-away: never treat a wall-clock timestamp as a uniqueness source without checking the platform's actual clock granularity; a UUID costs nothing here and removes the assumption entirely.

**2026-08-13 — Phase 4, manager view smoke test: Dormant-valuable was silently empty.**

Ran `db/manager_queries.py::recovery_pipeline` against the full seeded dataset to sanity-check the manager view before calling Phase 4 done, and it returned an empty list — zero outlets in the whole 820-outlet dataset landed in the "Dormant-valuable" segment. That's the segment the "recovery pipeline" section exists to show, so an empty result was suspicious enough to dig into rather than assume the data just has none.

Root cause was in `logic/segmentation.py::compute_valuable_threshold`, which I'd set to the 75th percentile of peak billing value across *every* outlet that has ever billed -- including outlets that are still Core today. Currently-thriving accounts keep compounding over the 6-month window and dominate the top of that distribution, so the 75th-percentile bar (₹15.48L) ended up higher than the single highest peak any *dormant* outlet had ever reached (₹7.9L). By construction, no dormant outlet could ever cross it. I picked 0.75 as a plausible-sounding default without checking whether it was actually reachable by the population it was meant to classify.

Fix: dropped the default to the median (0.5). At the median (₹4.08L), 21 outlets land in Dormant-valuable -- a real, checkable number I verified against `docs/data-notes.md`'s revenue-concentration finding. Also fixed a second, related issue the same smoke test surfaced: `conversation_quality`'s checklist-completion metric was reading 100% because every historical (pre-app) visit is seeded with `is_complete=True` as "a finished log entry" -- which is a true statement about the historical row but not an answer to "did BDMs finish the in-app checklist," since historical visits never went through this app's checklist at all. Restricted that metric to `source='app'` rows, and made it display "no app-recorded visits yet" instead of a misleadingly perfect 100% when there aren't any.

Neither of these would have been caught by the segmentation unit tests, which use small synthetic fixtures rather than the real distribution -- both only surfaced by actually running the manager queries against the full dataset and treating an oddly-round number (0) as a bug to investigate rather than a fact to report.

**2026-08-13 — Phase 5, independent review (fresh agent, no build context) caught two live bugs.**

Before finalizing, I asked a separate agent with no memory of this build to review the repo cold -- read the README, the code, and actually run it, rather than trust my own read of code I'd just written. It found two real, "ran without error, silently wrong" bugs, both worse than anything I'd caught myself:

1. **The reference "today" for recency math silently jumped 13+ days the moment any app visit was submitted.** `db/queries.py::_latest_known_date` used `MAX(visit_date)` across *all* visits (historical + app) as "today," reasoning that a fixed historical window needed a matching fixed reference point. But app-submitted visits are stamped with the real wall-clock date, weeks after the historical log ends. The agent reproduced it directly: one outlet's `days_since_last_visit` was 3, then jumped to 16 the instant an unrelated BDM submitted one unrelated visit elsewhere -- because "today" itself had just moved forward 13 days for the whole app, reshuffling every outlet's beat-priority score and every BDM's coverage-gap numbers nationwide, all triggered by a single unrelated write. My own testing never caught this because I was seeding once and reading immediately after, never comparing "before this write" to "after this write" for an unrelated outlet -- exactly the kind of check a fresh reviewer runs and a rushed self-check skips. Fix: just use `date.today()`. The "matching reference point" reasoning was solving a problem that didn't need solving -- a live tool's "today" should be today, and historical outlets correctly reading as long-overdue the moment the tool goes live is the true, useful signal, not a bug to design around.

2. **Streamlit's `st.radio` defaults to its first option, so an untouched checklist item read as an answered one.** Every outlet type's checklist has at least one blocker-type radio item. `st.radio(item["label"], item["options"], ...)` pre-selects `options[0]` the moment the screen renders -- before the BDM has looked at it, let alone answered it. `submit_visit`'s outcome-evidence check (`any(r["response_type"] == "blocker" and r["response_value"] ...)`) then read that untouched default as a real recorded outcome, which is enough to reach `Partial` confidence. The agent simulated a full click-through submit with zero real interaction -- no code, no order, no collection, nothing touched -- and it still stored `confidence = 'Partial'`, never `Unverified`. That's a direct hit against the one feature the whole verification design (see README's "Madurai decision") exists to protect: distinguishing a real conversation from a drive-by check-in becomes nearly impossible if the UI hands out free evidence by default. Fix: `st.radio(..., index=None)` so nothing is pre-selected, and treat a `None` choice as no answer rather than stringifying it into a fake response.

Both bugs share a pattern worth naming: they only show up by comparing state *across* an action (before vs. after a write; a full click-through vs. an empty one), which is exactly what a single-pass code read or a happy-path manual test misses. Neither was in the segmentation/scoring logic I'd already unit-tested hardest -- both were in the thinner, less-tested seams between the DB layer and the UI.

**2026-08-13 -- Post-launch, IT WORLD branding pass: a custom header rendered invisibly.**

After the client asked to reskin the app with IT WORLD's real brand colors (navy `#0B2D6B`, magenta `#D6266E`, pulled from it-world.in) and rename the nav tabs, I added a custom branded header (`render_brand_header()` in `app.py`) -- a gradient top bar plus an "IT WORLD · Field Sales" wordmark -- and reduced the page's top padding from `1rem` to `0.5rem` on the assumption that the extra room was no longer needed now that the header itself would fill that space.

It rendered completely invisibly. Not a crash, not an error -- `document.querySelector('.brand-header')` found the element, `getComputedStyle` showed correct navy text color, `opacity: 1`, `visibility: visible`, sensible coordinates well inside the viewport. Every signal said it should be showing. I only found the actual cause by asking `document.elementFromPoint()` what was *actually* at those exact pixel coordinates: a different `div` entirely (`st-emotion-cache-1j22a0y`) -- Streamlit's own sticky top toolbar (the "Deploy" / hamburger-menu bar every Streamlit Cloud app has), which sits fixed at the top of the viewport and was overlapping my header because I'd shrunk the padding that used to hold it clear.

Fix: restored generous top padding (`3.2rem`, enough to clear the toolbar) and dropped the negative margins I'd used to pull the gradient bar flush to the edge -- that instinct ("make it edge-to-edge") was exactly what pulled it back underneath the toolbar. Take-away: "the element exists with correct computed styles" is not the same as "the element is visible to the user" -- z-index/stacking-order bugs from a host page's own fixed chrome don't show up in any property read on the element itself, only in what's actually painted on top of it at that point.

**2026-08-14 -- GPS capture: worked on my machine, hung forever in production.**

Built the browser-geolocation capture for the Counter Conversation screen (see the GPS feature entry above -- device location as an anomaly/audit signal, never outlet identification). Tested it locally by simulating the callback's output as a URL parameter (`&cap_lat=...&cap_lon=...`) and confirmed the read side worked -- but never actually clicked the real button against a real GPS fix before calling it done, because the local dev sandbox has no location hardware to test against honestly.

The client did, on the real deployed app, and reported the button stuck on "Getting your location..." indefinitely. Reading the browser console myself (`read_console_messages` against the live Chrome tab) showed the real story in one line:

`SecurityError: Failed to set the 'search' property on 'Location': The current window does not have permission to navigate the target frame to '...&cap_lat=13.025...&cap_lon=80.208...'`

The geolocation call had succeeded -- that's a real GPS fix in the error message, not a null -- and the bug was one step later: my code did `window.parent.location.search = params.toString()` to hand the result back to the Streamlit app, which works fine on `streamlit run app.py` locally (the app IS the top-level page there) but throws on Streamlit Community Cloud, which wraps every app in its own sandboxed iframe for its "Hosted with Streamlit" chrome. `window.parent` from inside my `components.html` iframe resolves to *that* wrapping frame, not the app itself, and Chromium's sandbox model blocks a nested frame from navigating an ancestor via the `Location` setter methods. Locally there's one fewer frame in the chain, so the exact same code silently worked -- an environment difference invisible from inside the dev sandbox no matter how carefully I'd re-read the code.

Fix: replaced the `Location.search` assignment with a synthetic `<a target="_top">` click, which uses the browser's native link-following navigation instead of the `Location` object's setter API -- a different code path that Chromium's sandbox permits even where the setter is blocked. Take-away: a feature that depends on the browser's cross-frame security model cannot be fully verified from a dev environment that only has one frame layer -- "it works locally" was true and still an incomplete answer, and this one needed a real click on the real hosting platform to surface at all.

**2026-08-14 -- Noticed a second, more serious bug while investigating the GPS one.**

While looking at the live app to debug the GPS issue above, one of the client's own browser tabs was a Google search for `psycopg2.InterfaceError: connection already closed` -- evidence of a real error encountered separately, not something I reproduced myself first. I hadn't been asked to look at this; I went looking because the tab title was sitting right there and matched a failure mode I recognized as plausible for this app's architecture.

`app.py` caches one Postgres connection for the life of the process via `@st.cache_resource`, and the only error handling around it was `except psycopg2.Error: conn.rollback(); raise`. Supabase's Session pooler can close an idle connection server-side; the *client* only finds out the next time it tries to use that connection, and when it does, `psycopg2.InterfaceError: connection already closed` is exactly what's raised. I checked directly (closed a real connection, then called `.rollback()` on it): the rollback call itself raises the identical `InterfaceError` again. So the old handler's fix for "one bad query poisons every later query" (an issue from an earlier phase, see the `InFailedSqlTransaction` entry above) made this specific failure worse, not better -- it caught the dead-connection error, tried to roll back the same dead connection, and that second call threw an unhandled exception straight to the user, for every single request on that cached connection until the whole process happened to restart.

Fix (attempt 1): split connection creation (`_make_conn`, still `@st.cache_resource`) from a wrapper (`_get_live_conn`) that checks `conn.closed` before handing it out and clears the cache to force a fresh connection if so, plus a dedicated `except psycopg2.InterfaceError` branch *before* the general `except psycopg2.Error` one.

**This fix was itself wrong, and the client hit the exact same crash again minutes after I shipped it.** I'd guessed the exception type instead of reproducing it. When I actually killed a real connection's backend process directly (`pg_terminate_backend`, which is what a pooler recycling an idle connection does server-side) and drove the app against it locally, the traceback showed execution reaching `conn.rollback()` inside the *second*, generic handler -- meaning the original failure was `psycopg2.OperationalError` (a broken socket), not `InterfaceError`. `InterfaceError` is what `.rollback()` *itself* then raised when it discovered the connection was dead, one exception later. My `except psycopg2.InterfaceError` branch never had a chance to run because the wrong exception type never reached it. `conn.closed` didn't help either, as documented at the time -- it doesn't reflect a server-side close until the client actually tries to use the connection.

Fix (attempt 2, verified against a real killed connection, not guessed): wrap the rollback itself in try/except. Attempt `conn.rollback()` as before; if *that* raises any `psycopg2.Error`, that failure is the real signal the connection is dead (regardless of which specific exception type got there first) -- clear the cache and `st.rerun()`. If rollback succeeds, re-raise the original error as before. This is correct regardless of whether the dead-connection error surfaces as `OperationalError`, `InterfaceError`, or something else, because it doesn't try to predict the exception type at all -- it just asks "did the recovery attempt itself work?" Reproduced the original bug and confirmed the fix twice, both against a connection killed the same way the first "fix" failed to handle. Take-away: for a failure mode I couldn't trigger myself on demand, I wrote the handler around a guess of what the exception would look like instead of finding a way to actually produce it first -- the second attempt cost nothing extra once I'd built the `pg_terminate_backend` repro, and should have been the first move.

**2026-08-14 -- Static chart to interactive, camera to lazy, verified locally this time before touching production.**

Two client-requested changes, done together and both verified against a real local run (fresh embedded Postgres, fresh `streamlit run`, real clicks in a browser) before any deploy, per explicit instruction after the connection-recovery mistake above: fix and check locally first, deploy last.

1. The 6-month billing trend was a hand-built SVG sparkline (text-only, no interaction) -- replaced with a Plotly `go.Scatter` figure (`logic/charts.py`, `build_trend_figure`) rendered via `st.plotly_chart`. Kept the exact same three-way null rule the SVG version enforced (a real billed month, an explicit zero, and no record at all must never collapse into each other -- see docs/data-notes.md): a no-record month is `None` on the line trace with `connectgaps=False` so the line actually breaks, plus a separate hollow-marker trace at that x-position so the gap isn't simply blank; a zero-bill month stays connected but colored differently from a real number, with its own hover text ("billed nothing", never "no record"). Tests rewritten against the new Plotly figure object (`tests/test_charts.py`) rather than string-matching SVG output.

2. `st.camera_input` used to render directly inside the visit form, which means Streamlit mounts it (and the browser prompts for camera permission) the instant the Counter Conversation screen loads, whether or not the BDM ever intends to take a photo. Moved it out from inside `st.form` (forms only rerun on submit, so a checkbox inside one can't reveal a new widget immediately) to a `st.checkbox("Add a photo of the counter (optional)")` gate just above the form: `st.camera_input` is only called -- and the widget key only exists in `st.session_state` -- when that box is checked, and unchecking it pops the key so a stale photo can't linger. The submit handler reads `st.session_state.get("photo_input")` instead of a value threaded out of the form.

**2026-08-14 -- The `target="_top"` GPS fix above was itself still wrong, in a way neither of us caught until a real device tested it.**

The SecurityError fix earlier in this log (switching to a synthetic `<a target="_top">` click) shipped, and the client reported the *symptom* was gone -- no more stuck spinner -- but the Location section still showed the shop's own address, never the BDM's actual position. `target="_top"` doesn't mean "one level up" -- it means the single outermost frame in the whole tab. Streamlit Cloud's public URL wraps the app in its own hosting iframe, so from inside my `components.html` iframe the chain is three frames deep: the coordinates landed on that outer wrapper page's URL, which the Streamlit Python process never sees, one level short of where `target="_top"` actually lands. My own testing never caught this because I'd only ever tested against the app's internal `/~/+/` URL, which skips the wrapper entirely -- `_top` and `_parent` are indistinguishable from inside that URL, so the bug only exists on the link an actual user opens.

Given the choice between patching it (`target="_parent"`, which lands exactly one level up, on the app itself) or removing device capture altogether, the client chose to remove it -- Area/District fell back to the outlet's own registered coordinates, a fixed value that can never silently fail.

The client later asked for it back, having noticed the registered-address fallback doesn't reflect where the BDM actually is when testing from a different location. Same fix as identified above (`target="_parent"`), but this time proved *before* shipping, not after: built a throwaway 3-level nested-iframe test page (`outer.html` > `inner.html` > `gps.html`, served locally) that reproduces the exact frame depth Streamlit Cloud's wrapper creates, and drove synthetic clicks against both `target="_top"` (confirmed: lands on the wrong, outermost frame) and `target="_parent"` (confirmed: lands on the correct one) before writing a single line into the real app. Take-away: "I fixed the error" and "I fixed the behavior" are different claims -- the first fix made the exception disappear without ever checking that the feature did what it was for, and only a same-shaped harness (not the app's own dev URL, which hides the exact frame level in question) could have caught it honestly.

Verified by actually starting a clean embedded Postgres + `streamlit run` pair and clicking through it: My Visits (expander grouping), Counter Conversation (chart renders as a `.js-plotly-plot` element with working hover tooltips, camera stays uninitialized until the checkbox is ticked -- confirmed the "camera access requested" event only fires after that click, not before), a real visit submission round-trip, This Week, and Insights. All 55 tests pass.
